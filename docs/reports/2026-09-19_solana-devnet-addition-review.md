1. **Critical — The ledger cannot produce the advertised “affordable after Friday” result.** T4 defines only outflows. Within a fixed horizon, delaying payment cannot improve the final minimum when no inflows exist. Specify dated inflows, the horizon, and how earlier obligations carry forward when testing later payment dates—or remove the earliest-date feature. Add a reproducible fixture showing the promised “30 fails, 15 passes” result.

2. **Critical — Recipient token-account creation and its SOL cost are missing.** A valid recipient wallet address does not imply an existing DEMO associated token account. Specify idempotent ATA creation in the transfer transaction, include its rent funding in the SOL requirement, and test receipt verification when the recipient has no pre-transfer token-balance entry. Alternatively, explicitly restrict the spike to a pre-provisioned recipient. [Associated token account documentation](https://www.solana-program.com/docs/associated-token-account)

3. **Critical — Timeout recovery assumes a signature the application might never receive.** Submission can reach the network while its response is lost. Choose a signing flow that exposes the signature before broadcast, then retain the signature, transaction identity, and expiry information before sending. Define recovery across wallet-tab unmounts and page reloads; otherwise an unresolved transfer can disappear and permit a duplicate payment. Solana explicitly supports extracting the signature before submission. [Submission documentation](https://solana.com/docs/rpc/http/sendtransaction)

4. **Critical — “Expired — not sent” is stronger than the proposed evidence.** Passing `lastValidBlockHeight` establishes that the transaction cannot newly land; it does not establish that it never landed. A null `getSignatureStatuses` result can reflect a cache miss because historical search is disabled by default. Specify commitment levels, historical lookup, and how unavailable or inconclusive responses remain `unconfirmed`; only permit a fresh transaction after resolving the original. [Signature-status documentation](https://solana.com/docs/rpc/http/getsignaturestatuses)

5. **Critical — Review and signing lack an immutable payment identity.** Re-reading mutable form inputs at signing can silently change what was reviewed. Freeze sender, recipient, mint, network, amount, reserve, and schedule for the attempt; require another review when relevant inputs change. Acquire the duplicate-submit guard before the first asynchronous operation, including wallet approval. Reject stale balance and approval callbacks after account changes, following the existing request-generation pattern in [App.tsx](</Users/nathanstough/Desktop/VT Hacks/frontend/src/App.tsx:39>).

6. **Critical — Reconciliation does not define a consistent balance transition.** T6 can mark a signature reconciled before balance refresh succeeds, making retries no-ops while the outlook remains stale. Specify retryable receipt/balance loading and require a balance snapshot at the chosen commitment with a context slot at least as recent as the transfer. Atomically install that snapshot, remove the scenario, and add a history-only receipt so the transfer is not deducted twice. Test null receipts, refresh failures, and stale responses. [Transaction lookup](https://solana.com/docs/rpc/http/gettransaction), [balance response context](https://solana.com/docs/rpc/http/gettokenaccountbalance)

7. **Critical — The shipping dependency explicitly permits skipping the most consequential tests.** T8 depends only on T6, and the fallback drops `receipt` and `state` tests. Make those tests, the integrated build, and the failure-isolation check prerequisites to marking the feature shipped. Add deterministic RPC failure tests for ambiguous submission, expiry, delayed receipts, account changes, and failed reconciliation. If these cannot finish before code freeze, reduce scope or stop the workstream.

8. **Critical — There is no integration-and-deployment task joining the owner lanes.** The frontend owner’s import and the wallet module live in different worktrees; T1’s builds precede either change. Add a task that combines both changes according to `CLAUDE.md`, builds using the isolated dependencies, and deploys that checkout’s `frontend/dist`. Specify who owns it and when it gates T8. Also correct T1’s working directory: the npm manifest and lockfile are under `frontend/`, not the worktree root.
