1. **Critical — Cancelling a load leaves both account buttons permanently disabled.** `preset()` increments `loadSeq` and aborts the request, but does not clear `loading`. The aborted load’s `finally` then skips clearing it because its sequence is stale. Explicitly set `loading` to `null` in `preset()` and test selecting a preset during an outstanding load.

2. **Critical — Account replacement mixes the new account with the previous account’s solution.** `setBase()` changes the request and provenance immediately, while `res` remains unchanged until the debounced solve finishes. `PrescriptionList` still exposes the old plan’s checkboxes; clicking one introduces an invalid candidate lock into the new account. Chat likewise receives the new request with the old response. Make account transitions invalidate outstanding solves and hide or disable stale results and chat until a matching solution exists. Test with delayed responses and interaction during the transition.

3. **Critical — The read-only function cannot obtain its required window.** `read_back(account_id, config, *, expected)` receives neither the request nor its dates, yet must return `as_of` and `horizon_end` from that request. Pass the window explicitly. Also define opening-balance semantics when the requested start differs from the original seed window: a frozen creation balance is not automatically the opening balance for a later window.

4. **Critical — Malformed upstream responses escape the promised 502 boundary.** `client._request()` does not wrap JSON decoding failures, chained `.get()` calls fail on unexpected response shapes, and filtering only `date == ""` leaves invalid nonempty dates to fail response validation with a 500. Validate upstream envelopes and rows, use the existing `iso()` validator for usable dates, and translate malformed upstream data into `NessieUpstreamError`. Add invalid JSON, null envelopes, non-object rows, and invalid-date tests.

5. **Critical — The empty-account safeguard runs before rows are discarded.** Nonempty lists whose rows all lack usable dates pass the empty-list check and subsequently produce `scheduled=[]`. Read-only mode also lacks an explicit empty-schedule check after verifying the account object. Apply the no-empty-account policy after normalization as well, with tests for both modes.

6. **Critical — Existing transport errors do not ensure key redaction.** `client._request()` forwards upstream `message` values and `URLError.reason` verbatim; either can include the credential-bearing URL. The new handlers expose these strings directly. Sanitize errors at the transport boundary and test an upstream message and network exception containing the actual configured key.

7. **Suggestion — The provenance sentence misreports missing rows as changed amounts.** `not_round_tripped.length` includes missing and unusable-date rows, but the proposed wording calls all of them “changed by the sandbox.” Count distinct rows by reason and distinguish omitted rows from altered amounts. Specify whether an unusable-date row also receives “written but not returned” so it cannot be counted twice.

8. **Suggestion — New account provenance does not reset existing chat context.** `ChatPanel` retains messages and pending replies across account changes. An answer requested for the previous account can arrive beneath the new account, and subsequent requests include that previous conversation. Reset or explicitly separate conversations by account identity, abort pending replies on replacement, and test switching between two accounts with the same source.

9. **Suggestion — The withdrawal contingency contradicts the response contract.** “Not stored by the sandbox” is absent from the reason literal, and retaining local discretionary rows conflicts with treating `scheduled` as the read-back data. Remove the contingency or specify its schema, mixed-data provenance, counts, and tests before implementation.
