1. **Critical — D5’s serializer still throws on the proposed identity.** Converting only `p.amount` leaves `reserve` and every `schedule[].amount` as BigInts. Serialize and restore all monetary fields explicitly. Signed schedule entries need a signed parser; D2’s `toBase` rejects negatives. Test deep round-trip equality with a nonzero reserve and both positive and negative entries, rather than merely asserting no exception.

2. **Critical — D8 still does not define recovery from an ambiguous submission.** A frozen identity and an in-memory guard do not retain the submitted signature across reloads. Define a persisted attempt containing identity, signature, and expiry information, with persistence completed before broadcast. Solana permits extracting the signature before submission. Keep unresolved attempts blocking duplicate submission after restoration or account changes; test a lost submission response followed by reload. [Submission documentation](https://solana.com/docs/rpc/http/sendtransaction)

3. **Critical — D9 can atomically install a stale balance.** A successful refresh need not include the transfer. Require matching account/network/mint, a specified commitment, and a balance context slot at least as recent as the receipt’s slot. The atomic transition must also remove the payment scenario and insert a history-only receipt, otherwise the payment can remain deducted twice. Test stale snapshots, failed refresh followed by retry, and concurrent reconciliation. [Balance response](https://solana.com/docs/rpc/http/gettokenaccountbalance), [transaction response](https://solana.com/docs/rpc/http/gettransaction)

4. **Critical — Receipt verification has no executable acceptance contract.** D10 specifies one exceptional case but leaves “a `getTransaction` shape” undefined. Pin the supported encoding or normalized input, account matching, expected signature, mint, sender/recipient deltas, and `meta.err` checks. Network provenance must be supplied separately; the transaction response contains no genesis hash. Distinguish an absent recipient pre-balance entry from unavailable metadata, and test each mismatch independently against an otherwise valid receipt. [RPC response structures](https://solana.com/docs/rpc/json-structures)

5. **Critical — Same-day ordering can change the reserve verdict.** D1 describes walking individual entries, whereas the existing [simulator](/Users/nathanstough/Desktop/vthacks-solana/backend/app/solver/simulate.py:35) nets entries by day before measuring balances. Starting at 60 with same-day −20 and +20 produces an intermediate minimum of either 40 or 60 depending on input order. Specify daily aggregation or an explicit timing model, and test permutation invariance. Date-only entries cannot establish intraday order.

6. **Critical — “Earliest affordable date” remains under-specified and untested by the proposed beat.** Define the starting date, fixed horizon, payment placement, treatment of past entries, and carry-forward of obligations when evaluating later dates. “30 fails, 15 passes” can hold without any inflow and does not verify postponement. Add a fixture where the *same 30-token payment* fails today and first passes on a specific later date, plus a case where an earlier obligation prevents that result.

7. **Critical — Freezing review inputs does not establish affordability at signing.** D8 omits the earlier plan’s fresh balance check before signing. External spending between review and approval can invalidate the verdict while every frozen field remains unchanged. Define a state transition requiring refreshed balance evidence and another ledger evaluation against the frozen identity before approval proceeds. Test a balance decrease between review and signing and rejection of stale refresh callbacks.

8. **Suggestion — The mutation schedule does not support the “every guard” acceptance claim.** The listed mutations exercise ledger/state behavior, with none targeting units or receipt verification. Deleting a fixture row also changes test input rather than production behavior. Add named mutations for parsing, receipt identity/delta checks, and each state guard; mutate inflow handling in the ledger. Record which specific assertion detects each mutation.
